# Interpreter development

## When to use

The user wants to create an interpreter for a control system, add or fix NC words, adapt an interpreter to another
machine or postprocessor, find out why a program is simulated wrongly, or prepare an interpreter for a customer.

This skill has a general part that always applies, and five sections to turn to as the work goes on:

- "Inspect NC programs" — what the NC programs actually contain;
- "Develop native interpreters" — native DLL projects (Delphi, C++ or another native language), the INCT ABI, SNCI, Win32/Win64 builds, inheritance, protection and packaging;
- "Develop .NET interpreters" — the C# project, its files, the INI file, build and debugging;
- "How the kernel reads a block" — how the kernel reads a block and when your code runs;
- "Verify interpretation" — how to prove the change and what to hand over.

## Who you are working with

Assume the user is a CNC specialist — a technologist, a support engineer, a tester — with basic programming skills.
They know the machine and the control system far better than you do; they do not know compiler errors, git or
software jargon. So:

- explain each step in their terms: blocks, words, axes, cycles, the simulated toolpath;
- keep the code plain: one handler per word, names a machine operator recognises, a comment that says what a block
  does;
- never ask them to type a command or a path you can find yourself;
- when you need a decision, ask one short question and offer the options.

## Establish the facts first

Before planning anything, know these six things. Ask for what is missing instead of assuming it.

1. **The control system and its dialect** — maker, model, version, the G-code system (for example A/B/C on a lathe
   control), and the programming manual of that control. The manual is the specification.
2. **The machine** — the CAM project with this machine (`*.stcp`), its axes and their addresses in the machine schema
   (`X1`, `B1`, `Cs1`…), its channels, spindles and turrets.
3. **The starting interpreter** — an existing interpreter for this or a similar control, or the template it will be
   created from. Say which, and whether it is a copy you may change. The interpreters shipped with the product
   implement only what the product's own postprocessors produce, and some of them only import a toolpath: they do
   not link NC lines to the toolpath and may simulate with offsets or doubled approaches. Check the purpose of a
   shipped interpreter in the documentation's list of interpreters before you start from it or use it as a parent.
4. **The products** — which CAM system and Tuner versions must load the interpreter, and under which brand the
   customer uses them. Each product version has its own .NET version and its own SDK package version (see "The SDK
   package and the product versions" in "Develop .NET interpreters").
5. **The NC programs** — real programs from this machine: generated by its postprocessor, written by hand, from
   other CAM systems. Get several, not one. The postprocessor that produces them is worth having too: it shows which
   variants of each word will appear.
6. **The expected result** — what the simulation must show for each program: the toolpath, the tool changes, the
   spindles, the cycles. A reference from the real machine or a trusted interpreter is best.

Then check what you actually have: the .NET SDK, the installed products, the CAM log folder, Visual Studio Code with
the C# extension, a way to run an NC program through the interpreter without the user clicking (see "Run the
programs" in "Verify interpretation"). Report what is missing rather than substituting a guess.

## Trust order for facts

1. What the actual NC programs contain, and what an actual run of the interpreter produced.
2. The programming manual of the control system — authoritative for what a word means.
3. The templates and the SDK package shipped with the installed product — authoritative for what the interpreter
   can call. Never use a member the released package does not contain.
4. The user's written decisions in the workspace — authoritative for their machines and conventions.
5. Existing interpreters for the same control (C# or Delphi) — evidence of how a word was handled, and of which
   kernel limits had to be worked around; not a specification and not a style guide.
6. General knowledge, only when marked as an assumption.

A word that looks familiar from another control is not the same word. `M2=3` on one control is a spindle command,
`G33` with `I` and `K` has different meanings on different controls. Read the manual.

## Words of the documentation

The product's documentation on interpreter development names some things differently from this skill:

| Documentation | This skill |
|---|---|
| interpreter settings file | the `.snci` file |
| list of objects to interpret (`INCT_BlockExecArray`) | the execution queue, `Commands` |
| translation, interpretation | the read pass, the execute pass |
| former | toolpath former (`Create…Former`) |
| log of interaction with the interpreter | the CAM log with **Use log interaction with the interpreter** on |

## Workflow

1. Restate the task as an observable difference in the simulation, and name the acceptance check: which program,
   which block, what must happen.
2. Take the census of "Inspect NC programs" on all programs you have: which words occur, in which spellings, and
   which of them the interpreter does not understand yet.
3. Find the place in the interpreter that handles each word ("How the kernel reads a block" explains where to look),
   and explain the current behaviour before changing anything.
4. Decide what kind of change it is:
   - a **variation** an INI key of this interpreter already covers — another axis name, a machine M function, a word
     without effect on the toolpath: change `InterpreterSettings.ini`, not the code. An interpreter fresh from a
     template has almost no such keys; adding the key is a code change once, and every later variation of the same
     kind is a setting;
   - a **new behaviour** — a cycle, a frame, a feed mode: change the code as "Develop native interpreters" or "Develop .NET interpreters" describes, according to the library type, and build the moves of a cycle with the kernel's toolpath formers ("Toolpath formers" in "How the kernel reads a block");
   - a **kernel or SDK limitation** — the kernel does not offer what the word needs: say so, describe the workaround
     and its limits, and record what the product would have to change.
5. Make the smallest change, build it, run the programs again.
6. Follow "Verify interpretation": compare with the previous run on all programs, not only the one you fixed.
7. Report: what changed and why, the evidence, what is still not supported, and what the user must check.

## Rules

- Do not invent register names, kernel calls, SDK members or machine axis addresses. Read them.
- Do not change the installed product, its templates or its DLLs, and do not ask the user to.
- Do not turn an unknown word into silence. A word the interpreter does not simulate is either listed as "read
  without effect" (it does not change the toolpath in the simulation) or produces one warning per program.
- Do not call a change done without a run on the real programs: a successful build proves only that it compiles.
- Keep customer programs and projects out of the conversation where a reduced example will do, and never put
  licence data, passwords or customer archives into it.
- A package for a customer carries only the brand of the product the customer uses — in file names, paths, settings,
  comments and README alike (see "Prepare the package" in "Verify interpretation").

## Inspect NC programs

### When to use

Whenever the task depends on what the programs actually say: before adding or changing a word, when a program
behaves differently from another one, when programs from another postprocessor or CAM system arrive. An interpreter
is written for the programs the machine really runs, not for the manual's examples alone.

### Workflow

1. Collect every program and keep the originals (below).
2. Read the machine: axis addresses, channels, machine M codes.
3. Take the census of words and spellings.
4. Give every form a status and report what the interpreter must change.

### Collect every program

Ask for, and look for, all sources — each one brings variants the others do not:

- programs generated by the machine's postprocessor;
- programs written or edited by hand at the machine;
- programs from other CAM systems used on the same machine;
- examples in the customer's own documents (a `.docx` or `.pdf` with sample programs counts);
- programs inside archives attached to the request — unpack them, including nested archives.

Keep the originals unchanged; copy them into the workspace, one folder per source, so you can say later where a
variant came from. If two sources contain the same files, compare them byte for byte and keep one.

Read the encoding before reading the text. Programs from some controls are not UTF-8 (GBK, CP1251 and others occur),
and a file that mixes two encodings may not open in the CAM system at all — that is a property of the file, not of
the interpreter; report it and leave it out of the interpreter work. When you take program text out of a Word
document, keep the minus signs and hyphens: Word stores some of them as separate elements, and a naive text
extraction drops them, turning `Z-6` into `Z6`.

### Know the machine

The interpreter moves the axes of the machine schema, so the names in the program must be mapped to them.

- Read the axis addresses from the machine schema of the CAM project (the machine file of the project lists an
  `Address` for every axis — for example `X1`, `Y1`, `Z1`, `B1`, `Cs1`, `X2`, `Z2`). A project file can be unpacked
  with the project extractor of the CAM system.
- Read the channels: which axes, spindles and turrets belong to which channel.
- Get the machine maker's M code table if there is one. Codes that only switch something on the machine (clamps,
  doors, coolant variants, measuring) do not move it, but the interpreter must recognise them. Axis brakes are a
  case of their own: the SDK can switch the machine's automatic brakes, so ask whether brake codes must show in the
  simulation.

### Take the census

Strip strings and comments first — the comment characters of this control from its manual and from the
interpreter's analyzer settings (`;`, `(…)`, `"…"` strings and others) — then sort every word into a category, keeping its
spelling form separate. The categories that matter:

| Category | Examples | Why it matters |
|---|---|---|
| G functions | `G0`, `G17`, `G96`, `G710` | each needs a register value and a handler |
| M functions | `M3`, `M30`, `M120`, `M2=3` | standard ones are handled by the interpreter, machine ones go to the INI file |
| Axes without `=` | `X10`, `B90` | the kernel reads them as register values |
| Axes with `=` | `B1=90`, `C1=DC(0)`, `Cs1=IC(5)` | numbered axes and dimension functions are read by the interpreter itself |
| Spindles with a number | `S2=3000`, `M1=3`, `SPOS[1]=0` | which spindle the word belongs to |
| Other addresses with `=` | `CR=17.5`, `TURN=2`, `T="b3"` | values that are expressions or strings |
| Calls with brackets | `CYCLE81(…)`, `MSG("…")`, `WORKPIECE(…)` | cycles and procedures |
| Keywords | `TRAORI`, `DIAMON`, `SUPA`, `MCALL` | modes and transformations |
| Parameters | `R80=400`, `X=R80` | values computed from expressions |

For every form record how many programs use it and two or three of them. A form used by one program in fifty is
still a form the interpreter must handle or name.

### Map the census to the interpreter

For each form decide one of:

| Status | Meaning | What to do |
|---|---|---|
| Supported | the interpreter simulates it correctly | nothing; keep a program that uses it in the test set |
| INI file | a variant of something supported: another axis name, a machine M code, a word without effect | add it to `InterpreterSettings.ini`, adding the key once in code if the interpreter does not have it yet (see "Make variations a setting, not a code change" in "Develop .NET interpreters") |
| Code | a behaviour that changes the toolpath and is not implemented | implement it, with a test program |
| Not simulated | the simulation cannot show it, or the control's behaviour is unknown | read it, warn once per program, write it in the README |

The quickest way to fill the table is a run: send every program through the interpreter (see "Run the programs" in
"Verify interpretation") and collect the warnings of the CAM log — each unknown word, unknown axis and unsupported
cycle has its own message. Then look at the forms that produced no warning but may still be wrong: a word the kernel
skipped silently, an axis that moved in a program and stood still in another.

The kernel writes its messages about the words it reads, and the interpreter's own `Kernel.Log` lines, only when
**Use logs** and **Use log interaction with the interpreter** are on (System setup → Additional → Logs, the same in
the CAM system and in Tuner). Turn both on before the run, or the log stays empty.

### Rules

- Never edit a customer program to make it pass. The interpreter must read the programs as the machine gets them.
- Do not conclude "the program never uses X" from one program; check all of them, and say how many you checked.
- Examples written for another machine (a generic manual, a document for a different machine) show what the control
  can do; they are not proof that this machine's programs contain it. Mark which source a form came from.
- Report axis names together with the machine schema they were checked against.

### Done means

Every source of programs is listed with its file count; the census table exists with forms, counts and sample
programs; every form has a status; the machine's axis addresses, channels and machine M codes are known; files the
CAM system cannot read are named with the reason.

## Develop native interpreters

### When to use

Use this section for an interpreter compiled as a native DLL. It covers Delphi implementations and the same ABI implemented in C++ or another native language. Use "Inspect NC programs" before changing behaviour and "Verify interpretation" afterwards.

### Establish the native contract

Before editing code, identify the product version, target process architecture, native compiler/project, SDK type-library files and the exact `.snci` file. Read the installed type libraries (`STNCInterpreter.tlb`, `STNCAnalyzer.tlb`, `STNCFormers.tlb`, and `STNCConnect.tlb` when protected) instead of inventing declarations.

A native library must export two `stdcall` functions: `NCT_GetInterface: INCT_Interpreter` and `NCT_FreeMemory`. The product does not load a library that lacks either of them; `NCT_FreeMemory` may be empty when the library has nothing to release. Implement the ABI methods used by the product: `GetIdentifier`, `GetRegisters`, `SetInterface`, `Initialize`, `NextOperation`, `TransLine`, `DefineRegister`, `BeforeInterprete`, `Interprete`, `AfterInterprete` and `EndOfProgram` as needed by the control.

### Registers and their handlers

Keep an internal list of the registers the library declares, and bind the handler to each register when you add it — as the Delphi interpreters do with a `procedure(const BR: INCT_BaseReg) of object` field of the register, and as the C# base class does with the `command` parameter of `AddRegister`:

- In the constructor, add every register with its handler to the internal list. `GetRegisters` returns that list to the kernel as `INCT_RegisterList`.
- The kernel merges the registers of the `.snci`, of the library and of its parents into the base register list of `INCT_SysState`, so the position of a register there is not its position in your list. In `Initialize`, walk the base registers (`Get_BR_Count`, `Get_BR_ByIndex`), find your register by name and keep a map from the base register index (`BR.Idx`) to your register.
- In `Interprete(ExecNum)`, take the queue element with `BEA.Get(ExecNum)`. For a register element (`ExecType = exReg`), `ExecParam` is the base register index: take your register from the map and call its handler with the base register. For a command element (`exObj`), `ExecParam` is the command you added with `BEA.Add(exObj, …)`: run it in your command dispatcher.
- A base register the map does not contain — one that exists only in the `.snci` or in a parent — is not yours: leave it to the parent or ignore it.

With this, `Interprete` needs no `case` over addresses, and a new word is one line in the constructor and one handler.

### Project and platform

Keep the project and library names aligned with the `.snci`. Delphi projects normally use `.dpr` and `.dproj`; C++ projects must provide the same exports and ABI. Build Win64: current products are 64-bit and load the DLL named in `LibraryFileName_x64`; build Win32 only for a 32-bit product of an older version. Place the matching DLLs beside the `.snci` or in the package layout required by the product.

### SNCI and identifiers

For a native library fill `LibraryFileName_x64` (and `LibraryFileName_x32` only for a 32-bit product); do not fill `LibraryFileName_Net` or `NetNamespaceClass`. `LibraryID` in the `.snci` must equal the string returned by `GetIdentifier`. `ID` identifies the interpreter settings file. Both IDs must be unique. A child must set `ParentID` to the parent's `ID` and set `ParentFileName` to the parent's `.snci`; the parent's `LibraryID` is not a valid `ParentID`.

Check relative DLL paths, platform suffixes (`Win32`, `Win64`), register precedence and the parent chain before running a program.

### Inheritance and protection

A native child receives the parent `INCT_Interpreter` through `SetInterface`. The kernel itself calls the parent's `GetIdentifier`, `GetRegisters`, `SetInterface` and `Initialize`; the child must not call them. Call the parent's other methods as the documentation on interpreter inheritance recommends: `TransLine` when the child read nothing of the line (`ProcessedChars` is 0), passing on everything the parent returns; `DefineRegister` when the child did not define the register, passing on the index and the result; `Interprete` for an element the child does not interpret itself; `BeforeInterprete` and `AfterInterprete` always; `EndOfProgram` when the child did not detect the end of the program, returning the parent's result.

If the interpreter's container holds `<library-name>.dat`, the product supplies `INCT_Connect`. An interpreter loaded from an ordinary folder does not receive it, so test a protected interpreter from its container. Verify the secret data through `Get_Count`, `Get_Data` or `Get_SCData` before allowing interpretation. A protected interpreter must fail closed when the data is absent or mismatched. The kernel looks for the `.dat` by the name of the DLL it loads, so it is `<library-name>_Win64.dat` for `<library-name>_Win64.dll`. An interpreter that fails closed produces an empty toolpath without an error: when you see one, check the `.dat` and `INCT_Connect` first.

### Memory and unload

Release interfaces and objects owned by the library. Implement `NCT_FreeMemory` and ensure parent interpreters can unload after the child. Never keep CAM interfaces in process-global state; the product can create several interpreters at once.

### Build, debug and verify

Build unchanged sources first. Check exports, architecture, identifiers and the `.snci`/DLL pairing before diagnosing simulation. Run the real programs under CAM or Tuner, inspect the CAM log and use a native debugger when needed. Then follow "Verify interpretation" for every target architecture and product version.

### Package

Keep product-brand files, source paths, customer programs and build output out of the delivered package.

### Rules

- Do not change the kernel or product DLLs to make a native interpreter work.
- Do not assume Delphi-specific behaviour is part of the ABI; verify it against the type library and a working interpreter.
- Do not claim success from compilation alone: the native DLL must load and interpret the reference programs.

## Develop .NET interpreters

### When to use

Work on a C# interpreter: creating one, adding a word or a cycle, making it configurable, building it for the
products it must run in, debugging it. Take the census of "Inspect NC programs" first and follow "Verify
interpretation" afterwards; "How the kernel reads a block" explains the kernel calls this section refers to.

### Words used here

- **Product version** — the major version of the installed CAM system or Tuner (2, 3). Each has its own .NET version
  and SDK package version.
- **The `.snci` file** — the XML file that tells the CAM system which DLL is the interpreter. The documentation calls
  it the interpreter settings file.
- **The INI file** — `InterpreterSettings.ini` next to the DLL, read by the template at start. The template calls it
  the settings file; it holds the switches a user may change without building.
- **GUID** — a unique identifier such as `{5DD76B4D-8ABE-43EE-AB0C-078F5D686C5E}`; create a new one with
  `[guid]::NewGuid().ToString('B').ToUpper()` in PowerShell. The kernel accepts a GUID only in braces.

### Workflow

1. Choose the starting point and create the project (below). Say which you chose and why.
2. Set the SDK package version and the target .NET version for every product version the interpreter must run in.
3. Fix the known defects of the template you started from.
4. Build the project unchanged; if it does not build, stop and fix that first — nothing after it can be diagnosed.
5. Run the reference NC programs through it and keep the result as the baseline ("Verify interpretation").
6. Make one change at a time in the file of its role; make variations a setting of the INI file.
7. Build, debug or trace on a real program, then follow "Verify interpretation".

### Choose the starting point

1. **An existing interpreter for the same or a similar control** — prefer it when its behaviour has been checked on
   real programs. Copy it into a new folder and give the copy a new identity:
   - a new GUID returned by `GetIdentifier` in `Entry.cs`, written also into `LibraryID` of the `.snci` file (the two
     must be equal);
   - another new GUID in `ID` of the `.snci` file.
   Two interpreters with the same identifiers cannot be told apart by the CAM system.
2. **A template** — `Supplement\NCKernel\Templates` of the installed product contains `Mill`, `TurnMill` and the
   robot templates `ABB Robot` and `Kuka Robot`; check which of them your product has, because not every product
   version ships `TurnMill`. Create the project with the interpreter creator: **Create interpreter** in the utilities
   menu of the CAM system, or **Interpreter manager** in Tuner — both start the same program. It copies the template,
   renames the files after the new folder, fills in the SDK package prefix, the program file name in
   `.vscode\launch.json`, and one new GUID for both `GetIdentifier` and `LibraryID`. It refuses a folder that already
   exists. After it has run, check by hand what it does not do:
   - `ID` in the `.snci` file is still all zeros: write a new GUID there;
   - the SDK package version in the `.csproj` is the template's internal development version: replace it (see "The
     SDK package and the product versions" below);
   - the `.snci` lies in `bin\Debug\`, which is build output: move it to the project folder (same section);
   - the environment variable for the debugger is set only if you press the button that stores the program path in
     the creator's window, and only one of them (see "Debug" below);
   - the general fields of the `.snci` keep the template's sample values — `Description`, `CNCSystem`, `FileExtension`
     (`*.cnc` in `Mill`), `Authors`, `Company`, `Date`: fill them in for the real control;
   - `NetNamespaceClass` names the class the CAM system creates (`STNCInterpreter.Interpreter`, the class in
     `Entry.cs`): if you rename that namespace or class, change it too.

A child interpreter adds to a parent at run time; it is not a copy of the parent's sources. When the creator makes
a child, it writes the parent's `LibraryID` into `ParentID` and leaves `ParentFileName` empty. Correct both by hand:
`ParentID` must equal the parent's `ID`, and `ParentFileName` must name the parent's `.snci` — without it the kernel
loads no parent at all. A child calls the parent's methods where it adds to them (for example the parent's
`TransLine`), by the rules in "Inheritance and protection" of "Develop native interpreters", which come from the
documentation on interpreter inheritance and hold for .NET as well.

The creator makes the child from a full copy of the template, so it starts as a complete interpreter of its own: its
registers replace the parent's registers of the same name, and nothing in it calls the parent. The base class keeps
the parent as `ParentInterpreter`; remove what the parent must handle and call the parent's methods as the
inheritance rules say. The kernel finds the parent by the file name in `ParentFileName`: in the child's own
container, then in the container's folder, in the child's folder (including `.lnk` shortcuts to folders placed
there), in the product's interpreters folder and in its containers folder. It takes the first file with that name
and stops with an error if that file's `ID` differs from `ParentID`. During F5 the child's `.snci` lies in
`Bin\Debug`, so the parent must be found from there.

### The SDK package and the product versions

The interpreter references the package `<Org>.NCInterpreterSDK.Net`, where `<Org>` is the package prefix of the
product's vendor. Which version to use:

1. Read the version the installed product was built with: `Bin64\STNCInterpreterSDKProject.stbuildresult.json`,
   `build_results.versions`. It tells you the package prefix and the major version. Older Tuner installations do not
   have this file: read it from the CAM system of the same version. A version without a suffix in a product built on
   a developer's computer does not mean that the package was published.
2. Use the newest **released** version of the package (a version without `-dev`, `-rc` and similar suffixes, published
   on nuget.org) that has the same major version and is not newer than the version from step 1.

A nightly or test build of the product records a development version (`3.0.6-dev.2`): a customer cannot download it,
so never write it into a project that leaves your computer. Do not use a floating version (`3.0.*`) and do not choose
one from memory. A project with an unknown version or an unreplaced `$(package_namespace)` does not build; the
debugger start then fails, or the product loads an older DLL left in the output folder — check the build result
before judging the behaviour.

Each product version has its own .NET version: version 3 of the CAM system and Tuner runs .NET 10, version 2 runs
.NET 8. A product sold under another brand may use another package prefix and another version numbering; read both
from that product's own `stbuildresult.json` and never mix two prefixes in one delivery. One project can serve
several product versions: replace the template's `<TargetFramework>net10.0</TargetFramework>` with the list below and
give each target its own package version. If both properties stay, only one target is built. The robot templates
target `net10.0-windows`: there use `net10.0-windows;net8.0-windows` and the same names in the conditions.

```xml
<TargetFrameworks>net10.0;net8.0</TargetFrameworks>
<PackageReference Include="<Org>.NCInterpreterSDK.Net" Version="<version for product 3>" Condition="'$(TargetFramework)' == 'net10.0'" />
<PackageReference Include="<Org>.NCInterpreterSDK.Net" Version="<version for product 2>" Condition="'$(TargetFramework)' == 'net8.0'" />
```

The template's `.csproj` sets `OutDir` and `PublishDir` to `bin\Debug\`: with two targets both builds would write
into that one folder and overwrite each other. Make both depend on the target (`bin\Debug\<product version>\`). If
you remove them instead, `build` writes to `bin\Debug\net10.0` and `bin\Debug\net8.0`, but `publish` writes to
`bin\Release\<target>\publish\`, away from the folder the launch configuration uses.
Keep the `.snci` and `InterpreterSettings.ini` in the project folder, not in
`bin` (build output is not kept in version control), and copy them into every output folder:

```xml
<ItemGroup>
  <None Update="<Name>.snci" CopyToOutputDirectory="PreserveNewest" />
  <None Update="InterpreterSettings.ini" CopyToOutputDirectory="PreserveNewest" />
</ItemGroup>
```

**The folder name and the `.csproj` name must be identical.** The template's `.vscode\launch.json` passes
`bin\Debug\${workspaceFolderBasename}.snci` to the program, and its build task builds the project of the folder. With
several targets that path no longer exists: write one launch configuration per product version with the path of that
version's output folder. The template's `publish` task runs `dotnet publish` without a target; with several targets
give it `-f net10.0` or `-f net8.0`, one task per product version. Keep the `.snci`, the DLL name and
`LibraryFileName_Net` inside the `.snci` consistent.

### What goes where

The templates split the interpreter into files by role. Keep that split; a new feature goes into the file of its role.
Not every template has every file: `Mill` has no lathe cycles and no `Types.cs`; the robot templates read their
programs in `Interpreter.Transline.cs` and have no `Registers.cs` and no `IniFile.cs`; the ABB robot template also
has `Program.cs` and `AskUserForm.cs`.

| File | Contains |
|---|---|
| `Entry.cs` | the entry point the CAM system creates the interpreter through, and its GUID |
| `Interpreter.Registers.cs` | the registers: every address and G/M function the kernel reads itself, grouped as in the control's manual |
| `Interpreter.CommandHandlers.cs` | `Cmd…` methods called when a register of the block is executed (`G1`, `X`, `M3`) |
| `Interpreter.CommandTypes.cs` | the names of the commands a block puts into its queue |
| `Interpreter.Execution.cs` | executing the queued commands: motion, spindle, tool change |
| `Interpreter.Core.cs` | the state of the interpreter and the kernel calls (`TransLine`, `DefineRegister`, `BeforeInterprete`, `AfterInterprete`) |
| `Interpreter.Initialization.cs` | analyzer setup, machine axes, reading the INI file |
| `Interpreter.DrillingCycles*.cs`, `Interpreter.LatheCycles*.cs` | cycles and their move events |
| `Interpreter.Transline.cs` (robots) | reading the robot program statements |
| `Interpreter.Types.cs` | small types the interpreter uses |
| `IniFile.cs` | reading `InterpreterSettings.ini` |

A construction the kernel cannot read as a register — a numbered axis with `=`, an expression, a call with brackets,
a string — is read in `TransLine` (see "Words the kernel cannot read" in "How the kernel reads a block"); give such
readers their own file (`Interpreter.Statements.cs`, `Interpreter.Cycles.cs`, `Interpreter.ProgramFlow.cs`) when
there are many.

### Known defects of the templates

Check each one in the template you started from and fix it in your copy:

- **The INI file is never read.** `IniFile.cs` declares the Windows functions `GetPrivateProfileString` and
  `GetPrivateProfileSectionNames` without their Unicode names. Write `EntryPoint = "GetPrivateProfileStringW"` (and
  `…SectionNamesW`, `WritePrivateProfileStringW`) in each `LibraryImport`. Without it reading fails, the error is caught,
  and the log has only an information line starting with `Error reading settings file`, so every setting looks
  ignored and a log filtered by errors shows nothing.
- **The INI file is skipped when one interface is missing.** `Interpreter.Initialization.cs` returns before reading
  the file when the origin interface (`INCT_AddOriginByShiftAndRotate`) was not found, with only an information line
  in the log. Read the file independently of that interface.
- **Long values break reading.** `ReadString` passes the buffer size in bytes (`buffer.Length`) where Windows expects
  characters, so a value longer than 1023 characters (a long list of M codes) is written past the end of the buffer
  and reading fails. `GetSections` has the same error. Pass the size in characters and read again with a doubled
  size while the result fills the buffer (`size - 1` for a value, `size - 2` for the list of sections).
- **A one-digit tool number loads no tool.** `TurnMill` splits the `T` word in halves (tool, offset), so `T1` gives
  an empty tool part: no tool is loaded and `1` becomes the offset. Check against the `T` format of the control.
- **Lathe cycle register names disagree.** In `TurnMill`, the names looked up in `Interpreter.Core.cs` (`P LCYCLE`) and
  the names declared in `Interpreter.Registers.cs` must be identical; a difference silently reads the word as another
  register (see "Choosing a register by state" in "How the kernel reads a block").
- **Lathe cycles G70 and G73.** Check the feed of the finishing cycle G70 and the side the passes of G73 run on
  against the control's manual and a real program; both were found wrong in an interpreter built from this template.

When you fix a defect of a template in your interpreter, tell the user, so that it can be fixed in the template too:
a fix in your copy does not reach the next interpreter created from the template, and a fix in the template reaches
users only with a product version that ships it.

### Make variations a setting, not a code change

Programs of one machine name the same thing differently: an axis is `B90` in one program and `B1=90` in another,
the postprocessor of one shop writes M codes another does not. Put such variations into `InterpreterSettings.ini`
next to the DLL, so a support engineer can adapt the interpreter without building it.

The templates read only one key (`[Main] AddOriginFlipMode`) and ship no `InterpreterSettings.ini`. Every key below
is therefore written once in code — the key, its check and its log line — and from then on the variation is a
setting. A good set of keys:

```ini
[Axes]
; numbered machine axes that occur in the programs (axis addresses of the machine schema)
MachineAxes = B1, Cs1
; axis names of the control that differ from the machine schema: name in the program : axis of the schema
ChannelAxisNames = C1:Cs1, B:B1
[MachineFunctions]
; M codes of the machine that do not move it (clamps, doors, measuring)
M = 10, 11, 50, 51, 120, 121
[Words]
; words, addresses with a value, and calls with brackets that do not change the simulated toolpath
Keywords =
Addresses =
Procedures =
[Trace]
; yes - write every block and the commands it produced to the debug console and the CAM log
Enabled = no
```

Every key is read once at start, every malformed value is written to the CAM log as a settings error, and the values
taken are logged in one line, so the user can see what the interpreter uses. A value of the INI file is one line: INI
files have no continuation lines. A word the interpreter already knows must not be added again from the INI file: a
setting must not be able to switch off a supported word.

### Code style

Follow the style of the templates, so the code reads as one piece:

- names from the control's own vocabulary that a machine operator recognises (`CmdToolCall`, `CmdDwell`,
  `WorkpieceCoordinateSystem`), not internal jargon;
- one region per group of G functions, as in the control's manual;
- an English comment above each block saying what it does, and XML documentation on every method and field —
  interpreters are read by people with basic programming skills, so they carry more comments than other code;
- keep the state of the interpreter in fields of the interpreter object, not in `static` fields: the kernel creates a
  separate instance for every run, for the parent and for the contour of a cycle, each in a load context of its own,
  and the state must belong to the instance it describes;
- read numbers in programs with `CultureInfo.InvariantCulture`, so that `.` is the decimal separator whatever the
  Windows language is.

### Debug

You need Visual Studio Code with the C# extension of Microsoft (it contains the debugger the templates' launch
configurations use). The template's `F5` configurations build the interpreter and start the CAM system or Tuner with
it; a breakpoint in a `.cs` file stops when a program is simulated. The template's `launch.json` has three
configurations: **Launch CAM** starts `${env:NCKernelDir}/<program file>` with
`/Interpreter:<project folder>\Bin\Debug\<folder name>.snci`, **Launch Tuner** starts `${env:TunerDir}/ltuner.exe`
with `/i` and the same `.snci`, and **.NET Core Attach** attaches the debugger to a CAM system or Tuner that is
already running. The program folder is taken from the environment variables `NCKernelDir` (CAM system) and
`TunerDir` (Tuner). The interpreter creator stores one of them — the one of the product it was started from — when
you press its button for the program path, and it writes the program file name into `launch.json` in place of
`${env:CAMName}`; a project copied by hand keeps `${env:CAMName}`, which nothing sets, so write the file name there
yourself. The creator writes the variable into the user's environment and asks you to sign out of Windows or
restart the computer; at the least, close VS Code and start it again from the Start menu or Explorer, not from a
terminal that was open before. When a variable is missing, write the program path into `launch.json` instead — the
standard installation folder of each product, one configuration per product version, never a folder that exists
only on your computer.

Turn on **Use logs** and **Use log interaction with the interpreter** before debugging (System setup → Additional →
Logs, the same in the CAM system and in Tuner). Without them the log gets none of the kernel's messages about the
words it reads and none of the lines the interpreter writes with `Kernel.Log`. A message the user must see even with
the log off — a word that is not simulated, an interface that is missing — goes through `Kernel.Notify`, which shows
it in the notification panel.

To simulate a program: in the CAM system create an operation that works by an NC program, paste or load the program
text, choose the interpreter in the operation's strategy, and calculate the operation.

If a breakpoint is never hit, check in this order: the operation really uses your interpreter (not another one with the
same `LibraryID`); the build before the start succeeded (the template's build task keeps its terminal in the background — open the
terminal panel and read the build result); the
`.snci` passed to the program is the one in the output folder of the product version you started.

What the interpreter did with each block is visible through a trace you add once (the `[Trace]` key above, in a file
of its own such as `Interpreter.Trace.cs`): with `Enabled = yes` the block text and the commands it produced appear
in the debug console and, with the interaction log on, in the CAM log (`%AppData%\<vendor>\<product>\Version <n>\Log`).
If the CAM system reports only that the library does not support the interpreter interface, an exception was raised
while the interpreter object was being created — usually while creating the registers. Create the interpreter class
in a small console program with the same SDK package to see the real error message.

### Rules

- Do not change the product's templates, kernel or DLLs to make an interpreter work; record what the product would
  have to change instead.
- Do not use SDK members that the released package does not contain, even if a newer source of the SDK has them.
- Keep the project building after every change; make one change at a time.
- Do not put build output, customer programs or logs into the source tree.

### Done means

The project builds unchanged, then with the change, for every product version it targets, with a released SDK
package; folder, project, `.snci` and DLL names agree and both identifiers of the `.snci` are unique; the known defects
of the template are fixed or named; variations of the programs are settings with logged values; the code follows the
template's structure and style; the change was debugged or traced on a real program; and "Verify interpretation" has
been followed.

## How the kernel reads a block

### When to use

When you have to decide where a word belongs, when a word is read wrongly or not at all, and when the order of
actions in a block matters (a spindle before a move, a cycle after it). Read this section once before the first
change to an interpreter; "Develop .NET interpreters" refers to it.

### Workflow

1. Find the word in the census of the programs ("Inspect NC programs") and in the control's manual.
2. Decide which call reads it (the table below): the kernel itself through a register, `DefineRegister`, or
   `TransLine`.
3. Decide where its effect happens: in the handler of the register, in a queued command, or after the block.
4. Write a short test program with every spelling of the word and check the order of effects in the trace.

### Reading and executing a block

The kernel owns the program; the interpreter is called at fixed points. A block is handled in two passes. First the
kernel **reads** the whole block: every word it recognises is put into the block's execution queue, nothing is
executed yet. Then it **executes** the queue in order. In a C# interpreter derived from the template the calls are
overridden methods:

| Pass | When | Method | What it is for |
|---|---|---|---|
| start | once, from the constructor of the base class | `CreateRegisters` | declare every address and G/M function the kernel reads itself; field initializers have run, the body of your own constructor has not |
| start | for each interface the kernel hands over | `SetInterface` | keep the interfaces the interpreter needs (see "Interfaces" below) |
| start | once, after all interfaces | `Initialize` | set up the analyzer, the machine axes, read the INI file |
| read | before each word of a line | `TransLine` | read a construction the kernel cannot read as a register; it receives the rest of the current line |
| read | when the kernel meets an address | `DefineRegister` | choose which register an address means in the current state |
| execute | once, after the block is read | `BeforeInterprete` | decisions that need the whole block, before anything in it is executed |
| execute | for each element of the queue, in order | `Interprete` | a register element calls the register's handler (`Cmd…`); a command element calls `ExecuteParameterCommand` |
| execute | after the queue is done, unless `EndOfProgram` stopped it | `AfterInterprete` | what must happen after the block: a modal cycle call, resetting one-block states |
| start | when the next operation starts | `NextOperation` | reset what a new operation must not inherit |

Consequences that explain most surprises:

- The handler of a register (`CmdX`, `CmdG`) runs in the execution pass, after `BeforeInterprete` and in the order
  the words stand in the queue — not while the block is read.
- A handler usually does not move the machine itself: it stores the value and adds a command to the queue
  (`Commands.Add`). A command added during execution goes to the end of the queue, after all register elements of
  the block, so the motion of the block is executed once every word of it has been seen. A command added in
  `TransLine`, while the line is read, stands in reading order among the words.
- The kernel skips queue elements that were already executed and stops executing the block when the program has
  ended (`EndOfProgram`); `AfterInterprete` is then not called for that block. The base class of the C# SDK sets its
  end-of-program flag back to `false` only in its constructor: reset it in `NextOperation` if one interpreter serves
  several operations.
- `TransLine` sees the rest of the current line before every word, so it is the place for anything the kernel's
  own reader cannot handle.
- How a word without a value is read depends on the register's `valueAvailability`, in every interpreter:
  `vatOnlyAddr` — the word is only an address (`STOPRE`) and the kernel does not look for a value; `vatValue` — a
  value is required: `X` alone is reported as an error ("Value or expression is expected") and never reaches the
  queue; `vatBoth` — the value may be absent: `X` alone reaches the queue with an empty value. Whether the control
  accepts a word without a value is therefore decided when the register is declared, not in its handler. In a C#
  interpreter the base `Interprete` replaces the empty value with `0` only for `vatBoth` registers whose
  `CanUpdateEmptyValue` you override to return `true`. All registers of the templates are `vatValue`.
- A block whose queue stays empty — a line with only a comment, or a line that `TransLine` read completely without
  adding anything to the queue — gets no `BeforeInterprete`, `Interprete` or `AfterInterprete` at all; whatever you
  reset after every block in `AfterInterprete` is not reset for it.

### Native ABI and lifetime

The product loads a native DLL through NCT_GetInterface, checks GetIdentifier against LibraryID, obtains GetRegisters, passes interfaces through SetInterface, then calls Initialize. During interpretation it may call NextOperation, TransLine, DefineRegister, BeforeInterprete, Interprete, AfterInterprete and EndOfProgram. At unload it releases the interpreter and calls the library's NCT_FreeMemory contract before unloading parent libraries. A native implementation must preserve COM reference ownership and calling conventions. A .NET interpreter is loaded differently: the kernel loads the assembly into a load context of its own, creates the class named in `NetNamespaceClass` and calls its `NCT_GetInterface` and, at unload, `NCT_FreeMemory` by reflection. In both cases the parent is loaded and initialized before the child, and if the interpreter implements `INCT_InterpreterState`, its `Load` is called between `SetInterface` and `Initialize`.

### Interfaces

The kernel hands its interfaces to `SetInterface` one by one. One object — the toolpath (CLData) object — carries
many interfaces at once, but it arrives in a single call, and the base class keeps it only as `CLD`: its other
properties (`AxesBrakes`, `Comment`, `CutTo5d`, `OriginShiftRotate`, `PocketCycleFormer`) stay empty. Take every
additional interface from that CLData object in your `SetInterface` override, as the templates do for the origin
interface:

```csharp
if (interfaceObj is INCT_CLData_AutoAxesBrakes brakes)
  _axesBrakes = brakes;
```

When the `.snci` sets `UseGeomCLData`, the kernel hands over a geometric toolpath object instead of the CLData
object. The base class keeps it only as `Comment`, so both `GCLD` and `CLD` stay empty: take `INCT_GeomCLData` from
it in your `SetInterface` override too. The geometric object has no origin, brake or wait interface.

When a stock removal cycle reads its contour through the kernel's stock removal former, the kernel runs a second
instance of the interpreter over the contour blocks and hands it a cycle geometry object in place of the CLData
object. That object offers only the basic `INCT_CLData`, which the base class does not keep at all, so `CLD` is empty
and the extra interfaces are missing in that instance; with `UseGeomCLData` the instance gets the geometric object
instead, as above. The kernel ignores every error of that run: if `Initialize` throws because `CLD` is empty — the
`TurnMill` template does, when it creates its linear motion former — the contour stays empty without any message.
Make `Initialize` work without `CLD`, and test a stock removal cycle on a real program.

That second instance starts fresh: it does not know the plane, the units, absolute or incremental mode or diameter
mode of the program around the cycle. Pass them through `INCT_InterpreterState`: the kernel calls `Save(out state)`
on the running interpreter and its parents before the cycle, and `Load(state)` on the new instance between
`SetInterface` and `Initialize`. Every native turning interpreter implements it; the C# base class and the templates
do not.

Check in `Initialize` that each interface you need arrived, and report it if it did not: a `Kernel.Log` line is written
only when **Use logs** and **Use log interaction with the interpreter** are on (System setup → Additional → Logs), so
use `Kernel.Notify` for what the user must see.

### What the kernel reads by itself

The analyzer settings set in `Initialize` (through `Analyzer`) decide what the kernel reads without the
interpreter: which characters open and close a comment, whether `X=10` assigns a value, block numbers, upper and
lower case. The templates differ here — one accepts `(`, `(*`, `!` and `;` comments,
another only `(` — so take the comment characters of the census from the control's manual and from these settings,
not from the template you happen to start from.

Brackets set there become separate symbols only when `=` is allowed, and the kernel never reads a bracketed
expression as a value: `X=(10+5)` is reported as an error. A string after `=` keeps only its digits and points: with
quotes set in the analyzer, `T="b3"` is read as `T=3`. Read such forms in `TransLine`.

Other settings there change what a line is. `UnionLineChars` joins lines that end with a continuation character
(`~` in Heidenhain programs) into one block — use it instead of `nextLine` where the control has such a character.
`EndOfLineChars` splits a line at a separator such as the `;` of robot programs, and `ExcludeEOLChars` decides
whether the separator is passed on to the interpreter. `LineBeginWithNumber` skips a number at the start of a line,
such as a Heidenhain block number.

### Registers

`AddRegister(address, id, name, comment, sign, point, beforePoint, afterPoint, isLeadingZeros, isTrailingZeroes,
valueAvailability, values, isModal, command)` declares one register:

- `address` — the letters of the word (`G`, `X`, `TRAORI`); `id` — for an axis, its address in the machine schema, so
  the kernel can find the machine axis; `name` — a unique name, used to look the register up;
- `sign`, `point`, `beforePoint`, `afterPoint`, leading and trailing zeros — how a value of this address is written;
- `valueAvailability` — whether the word has a value (`X10`, `vatValue`), has none (`STOPRE`, `vatOnlyAddr`), or may
  have either (`vatBoth`);
- `values` and `isModal` — for a group of G or M functions, the allowed values and whether the group is modal;
- `command` — the handler called when the register's element of the queue is executed.

Group G functions as the control's manual does, one register per group: the kernel then knows that `G1` replaces
`G0`. `isModal` does not make the kernel skip a word whose value did not change: every word written in a block
enters the queue again, so the handler of a modal group runs each time the word is written.

**Keep `afterPoint` at the number of digits of the axes.** The kernel derives its axis tolerance from the register
with the most digits after the point, and checks arcs against ten times that tolerance. One register with four
digits — a thread lead, for example — makes the arc check ten times stricter for the whole program, and arcs whose
centre was rounded to the thousandth by the postprocessor are replaced by straight lines with a warning. The value of
a register is not rounded by `afterPoint`; it affects only how the register is written.

### Words the kernel cannot read

The kernel reads a register value only in simple forms. Read these in `TransLine` instead, report exactly how many
characters you read (`processedChars`), and add the work to the queue:

- numbered addresses with `=`: `B1=90`, `S2=3000`, `M1=3`. The kernel can read them itself if you declare a register
  with the address `B1` and allow `=` in the analyzer, but then a plain word with the same letters and digits — `B1`
  for the B axis at 1, `M1` for the optional stop — is read as that register, not as `B` or `M` with the value `1`.
  Read such addresses in `TransLine` when the programs also contain those plain words;
- expressions and dimension functions: `X=R80`, `Cs1=DC(0)`, `Z=IC(-2)`;
- calls with brackets and strings: `CYCLE81(…)`, `MSG("…")`, `T="b3"`;
- program flow: labels, jumps, `IF … ELSE … ENDIF`.

A subprogram call is not done by reading text in `TransLine`: take the part of the program from
`Kernel.ProgramManager` — `GetPartByLabels` or `GetPartByIndex`, or `GetPartByLabelsFromCurPos` and
`GetPartByRegisters` of `INCT_ProgramManager2` — and run it with `Kernel.DoSubprogram(part, count)`, as the templates
do for a subprogram call. For a program that consists of several files, set the order of the files with
`ProgramManager.AddToOrderList`.

Leave to the kernel what you did not read. Two flags change how the kernel continues after `TransLine`:
`breakLine` ends the block at this point — what was read is executed now, and the rest of the line is read as the
next block; `nextLine` asks for the next line of the program
to be read into the same block without executing the current one first — use it for a statement that continues on
the next line, not to skip the rest of a block.

### Choosing a register by state

The same address can mean different things: `F` is a feed, but a dwell time in a `G4` block and a thread lead in a
`G33` block. `DefineRegister(address, out index)` is called when the kernel meets an address; return the index of the
register the address means in the current state, or return `false` to let the kernel choose by its own rules. Only
the words to the left are known at that moment: the template decides by the commands already in the queue, so in
`F2 G4` the `F` is still read as a feed. If the control allows such an order, read the block in `TransLine` first. Check
every register name you look up there against `CreateRegisters`: a misspelt name makes the lookup fail and the kernel
reads the word as the default register of that address; only the interaction log, when it is on, shows which
register was chosen ("Register is defined: … name …"). A misspelt name of the register a condition depends on does
the opposite in the templates' `DefineRegister`: the condition register stays `null`, the condition is not checked,
and the alternative register is chosen every time.

### The execution queue

A handler adds a command with `Commands.Add`; the queue keeps each command once per block. When an effect must happen
before the motion of the block — a spindle start, a tool length — use `Commands.InsertBefore(CommandType.Move,
CommandType.<effect>)`, and know its limits: it does nothing if the command is already in the queue, and it adds the command to
the end if the move command is not in the queue yet. Call it before the move command has been executed: if the move
is already done or is being executed, the inserted command is placed in front of it and never runs, and the element
being executed runs a second time. Effects of one block that the control applies in a fixed order
(spindle before motion, motion before a modal cycle) must be ordered by the interpreter, not by where the programmer
happened to write the word. Whatever you compute while adding a command is computed at that moment, not when the
command is executed.

### Toolpath formers

The kernel builds the moves itself; the interpreter fills in a former and starts it. Before writing the moves of a
cycle, look for its former. The toolpath (CLData) object creates `CreateLinearMotionFormer`,
`CreateCircularMotionFormer`, `CreateDrillingCycleFormer` (simple, with shift, peck), `CreateLatheCycleFormer`
(grooving, thread cutting, stock removal) and, through `INCT_CLData2`, `CreateMillingCycleFormer` (thread milling);
`INCT_CLData_PocketCycleFormer` creates the pocket former. Adjust a former through its events, as the templates do in
their `…CyclesEvents.cs` files, rather than computing the moves yourself. The documentation describes every former
and its parameters.

### Machine axes

X, Y and Z are the geometry axes of the operation's channel; the templates link them to the axes of the channel at
initialization, and `TurnMill` links them again after a tool change whose `T` word is non-zero and has two or more digits
(tool and offset); `Mill` does not. A machine whose tool change moves the work to another set of axes needs that link in its
own tool change. Other axes are found by their address in
the machine schema. A word whose axis the schema does not have produces a warning once and moves nothing; when the
programs use another name for an axis of the schema, map it through the INI file (see "Make variations a setting,
not a code change" in "Develop .NET interpreters") instead of renaming the axis in code.

The SDK can also switch the automatic axis brakes of the machine (`INCT_CLData_AutoAxesBrakes`, taken from the
CLData object as shown in "Interfaces" above). Decide with the user whether brake M codes must change the simulation or
can be read without effect. To show a brake code explicitly, switch the automatic brakes off and write the brake
commands through `INCT_CLData_BreakCommand` of the CLData object: `Open`, `SetBreak(axisIndex, on)` for each axis,
`Close`.

### Channels

Each channel of a multi-channel machine is simulated as its own operation with its own program. From product
version 3 the SDK has a wait point, `INCT_CLData_Wait.AddWait(id)`, which the CAM system uses to synchronise
channels: a channel that reaches a wait point waits for the other channels with the same point. Take it from the
CLData object (`if (CLD is INCT_CLData_Wait wait) wait.AddWait(id);`). To make a control's wait word (`WAITM`,
`M200`, a wait mark) synchronise channels, translate it into `AddWait` with an identifier both programs share, and
check in the simulation that the channels wait as they do on the machine. The released SDK for product version 2
has no wait point: there the wait word can only be read without effect. An interpreter that only reads the wait word, so that the programs
are not rejected, must say in its README that the channels are not synchronised.

The equipment object also tells the interpreter which channel its program belongs to: take `INCT_Equipment_Channels`
from it (`if (EQ is INCT_Equipment_Channels channels)`) and read `CurrentIndex`, `Count` and `Channel[i].Name`.

### Known traps

- A thousandth-rounded arc becomes a line: see `afterPoint` above.
- A misspelt register name in `DefineRegister` reads the word as another register without an error: see above.
- Keep the state in instance fields and reset it in `NextOperation` where a new operation must not inherit it. In a
  native DLL, global data is shared by every instance of the interpreter in the process. A .NET interpreter is loaded
  into a load context of its own for every instance, so its static fields are not shared — and do not carry anything
  to the parent or to the contour instance either.
- A coordinate that is absent and a coordinate that is zero are different things; keep them apart in the state (see
  the empty value above).
- A registered word without a handler, or a handler that is never called for one of its values, fails silently;
  keep a test program for each group.
- A fractional G function (`G33.1`, `G12.1`) is not an integer: list the value with its fraction in the register's
  values (`[12, 12.1, 13, 13.1]`) and compare the register's decimal value (`register.Flt is 12.1`), as the template
  does, never an integer value.
- Registers written in the `.snci` file are loaded first, and a register of `CreateRegisters` is added only if no
  register of the same name exists yet: a register someone added to the `.snci` under the same name silently
  replaces its address, format and values, while the handler of the code is still attached to it by name. Look there first when a word behaves
  differently from what the code says.
- An exception in `CreateRegisters` or the constructor is reported by the CAM system only as an unsupported library;
  see "Debug" in "Develop .NET interpreters" for how to see the real error.
- An exception that leaves the interpreter while a program is interpreted — in `Interprete`, for example — ends the
  calculation of the whole operation, and only its message is left. Catch what you can handle, and report a word you
  cannot simulate as a warning instead of throwing.
- In a C# interpreter, an `Initialize` override must call `base.Initialize()`: it links the registers to their
  handlers by name, and without it no `Cmd…` handler runs. `Commands` is still `null` inside `CreateRegisters`, and a
  second register with a name already used is ignored without an error.

### Done means

You can say for each word of the change in which call it is read, where its value is stored, which command it adds
to the queue, and where that command produces its effect — and the order of effects within the block is the
control's, not an accident of the word order.

## Verify interpretation

### When to use

Before an interpreter change is presented as a result, and before an interpreter is handed to a colleague or a
customer — regardless of how cleanly it built.

### What you need

The reference NC programs ("Inspect NC programs"), the CAM project with the machine, the interpreter built before
and after the change, the products it must run in, and the expected behaviour. If there is no result of the
unchanged interpreter yet, produce one first: without a baseline every difference is unexplained.

### State how far the check went

Report exactly one of these, and never upgrade it without the evidence:

| State | Requires |
|---|---|
| **Not verified** | only a plan, a diff or a build exists |
| **Technically verified** | the interpreter loaded and the programs ran; the log and the simulated commands are kept, but not compared or reviewed |
| **Verified on the reference programs** | all reference programs ran before and after, every difference is explained, the warnings of the CAM log are reviewed, every targeted product version was checked |
| **Accepted for the machine** | the user or the customer confirmed the simulation for a specific machine — you cannot assign this state |

### Workflow

1. Get or produce the baseline: the result of the unchanged interpreter on all reference programs.
2. Run all reference programs through the changed interpreter.
3. Compare the summaries, then the simulated commands, then the warnings (below).
4. Repeat for every product version the interpreter targets.
5. State the verification state with its evidence.
6. For a hand-over, prepare the package and run its checks.

### Run the programs

To run one program by hand: in the CAM system create an operation that works by an NC program, paste or load the
program, choose the interpreter in the operation's strategy, calculate the operation, then read the simulation and
the CAM log. Do this to look at one block; do not rely on it for the whole set.

Turn on **Use logs** and **Use log interaction with the interpreter** before any run (System setup → Additional →
Logs, the same in the CAM system and in Tuner). Without them the CAM log has none of the kernel's messages about the
words it reads and none of the lines the interpreter writes with `Kernel.Log`, and a comparison of warnings compares
nothing.

Running a program by hand in the CAM system for every change does not scale. Use a runner that, without the user
clicking: opens the CAM project, creates an operation that simulates an NC program with the interpreter, calculates
it and writes the simulated commands to a text file, and copies the CAM log of that run next to it. Such a runner is
a small program that drives the CAM system through its programming interface (API); keep it in the interpreter's repository, in a folder of
its own with its own README, and never ship it to a customer. Run it on a copy of the installed product folder when it needs files next to the kernel, never inside the
installed product. The console of the kernel may print licence data: never save or show that output; keep only the
lines your runner writes itself.

For every program keep: the simulated commands, the warnings and errors of the CAM log, and a one-line summary
(errors, warnings, exceptions, skipped words, number of commands). Run the programs one after another: runs that
share the CAM log must not overlap.

### Compare

1. Compare the summaries of all programs before and after. A changed number of warnings or commands in a program the
   change was not meant for is the first thing to explain.
2. For every changed program, diff the simulated commands and start at the first difference. Trace it to the block
   and the word that produced it. An unintended difference matters more than an intended one.
3. Read the warnings, not only their count. Each warning names a word, an axis or a cycle; check that the ones left
   are expected (a word the machine schema does not have, a cycle that is not simulated) and written in the README.
4. Test the edges the programs do not cover with a short program of your own: the word with every spelling found by
   the census, at its limits, missing, repeated, in an unusual order.
5. A difference that is caused by the test setup and not by the interpreter (another coordinate system of the test
   operation, a different machine in the project) is not a result: say what it is and leave it out.

Some results vary between two runs of the same input — a warning that appears in one program in one run and in
another in the next. Run the program alone again before calling it a regression.

### Check every product version

Build and run for every product version and architecture the interpreter targets, in the CAM system and in Tuner where both are targeted. For native DLLs, build and load the Win64 binary (and a Win32 one only if a 32-bit product is targeted) and verify the exports, `.snci` fields and `LibraryID`/`GetIdentifier` pair. For .NET, each product version has its own .NET version and SDK package (see
"The SDK package and the product versions" in "Develop .NET interpreters"). Where a version cannot be run on this
computer, say so instead of implying it was checked.

### Native checks

For a native interpreter, keep a Win32 output, if there is one, apart from the Win64 one, test the matching `.snci` on an unchanged installation, and verify `NCT_GetInterface`, `NCT_FreeMemory`, parent loading and protected `.dat`/`INCT_Connect` behaviour when applicable. Compilation without a loaded simulation is not verification.

### Prepare the package

What a customer gets is one folder per product version with the `.snci`, the interpreter DLL and
`InterpreterSettings.ini` kept together — and the `.deps.json` only if loading needs it, which you check on an
unchanged installation. The build output holds more than that: the SDK package copies
`STNCInterpreterSDKProject.stbuildresult.json` into it, which names internal build pipelines and a user, and there
are `.pdb` and SDK `.xml` files and, after `publish`, the SDK DLLs (the helper, `STNC*.dll`,
`Geometry.VecMatrLib.dll`, `InteropTypes.dll`, `STTypes.dll`), which the product ships itself. Copy the files you need by name
instead of zipping the output folder. Add a README in plain language — what is supported, the limits, the settings,
how to debug — and, when the customer asks for them, the sources without `bin` and `obj`.

Before it leaves:

- **Only the brand of the product the customer uses.** The same product may be sold under different brands, and the
  customer must not find the other brand anywhere. Search the content of every file in the package, inside the
  archive, for the other brand's names, package prefixes, folders and servers — in file names, paths, settings, launch configurations, package
  references, comments and the README. Search the bytes of each file in both encodings Windows programs use for text (UTF-8 and UTF-16), starting at every
  position, not the text an editor shows: strings inside a DLL are not aligned, and decoding a whole binary file loses some of them. Add a
  control word you know is present and check that the search finds it.
- **No traces of this computer.** No user names, home folders, internal servers or internal package feeds in any file;
  launch configurations point at the standard installation folders of the products, not at folders of this computer.
- **The customer can build it.** The SDK package version in the project is a released one, available on nuget.org;
  your own test tools (the program runner, scripts, test programs of other customers) are not in the package.
- **It works on an unchanged installation.** The package must not depend on files you changed in the product or on a
  package version the customer cannot download.
- Build the package from sources saved in version control (a commit), and record which commit it was built from.

### Rules

- A successful build, a zero exit code or a plausible-looking toolpath is not verification.
- Do not change the reference programs, the machine or the project to make a comparison pass.
- Do not describe a result as accepted for a machine, and do not send a package anywhere without the user's
  explicit permission.
- Do not claim a check on a product version, a machine or a simulation that was not run.

### Done means

All reference programs were run before and after, every difference is explained at block level, the remaining
warnings are reviewed and documented, every targeted product version was built and run or its gap is stated, the
verification state is stated with its evidence, and — for a hand-over — the package passed the brand, trace and
unchanged-installation checks.

## The workspace

You have no memory between sessions; the workspace is it. Keep in the user's workspace, next to the interpreter: a
short `AGENTS.md` with the machine, the control, the products and the rules of the work; the reference NC programs
and their expected results; one short note per solved case in `notes\`. At the end of a task write down what was
wrong, how it was found and what fixed it.

## Done means

The change is minimal and explained, it is based on words read from the real programs and on the control's manual,
the interpreter builds for every product version it targets, all programs were run and compared with the previous
result, every word the interpreter does not simulate is named, and the checks left to the user — the simulation on
the machine, the customer's acceptance — are stated explicitly.
