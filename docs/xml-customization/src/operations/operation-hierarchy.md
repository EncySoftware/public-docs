This appendix to [Operation XML descriptors](operation-xml-descriptors.md) maps the full inheritance tree of
the technological-operation descriptors that ship with the CAM system. Use it to
**choose a base type to inherit from**: find the shipped operation closest to what
you want, then derive your operation from it (or from one of its bases).

The data combines the operation registry reported by the running system with the
descriptor declarations in the XML files, so IDs, captions, parents, container
classes, container IDs, solvers and source files are the real, current values.

## How to read this table

- **Rows are ordered depth-first** from the most abstract root
  (`TOperationDescriptor`) down to concrete operations. The **Lvl** column gives the
  inheritance depth and **Parent** names the type each row derives from; together
  with the ordering they reconstruct the full tree.
- **ID** — the descriptor ID. This is the `type=` value you put on your own
  operation to inherit from it, and (for concrete operations) the `TypeName` used
  in the registration record. Always shown, including for abstract base types.
- **Caption** — the human-readable name shown in the UI.
- **Parent** — the descriptor this one derives from.
- **Container class / ContainerID** — the Delphi **container** that represents the
  operation in the operation tree, builds the instance from the XML descriptor,
  owns it, and either computes the toolpath itself or delegates to a solver. The
  cell shows the class name on the first line and its class GUID (`ContainerID`) on
  the second. See *Container, solver and toolpath* in
  [section 4.3](operation-xml-descriptors.md#containerid-and-solverid--container-solver-and-toolpath).
  Every operation has a container. **Abstract base types** (rows that are not
  registered, instantiable operations) show the container they declare or inherit;
  the most abstract descriptors fall back to the base container `TSTAbstractTechOp`.
  Abstract bases are often the best inheritance targets for a new operation.
- **Solver class / SolverID** — the toolpath **solver**, shown the same way as the
  container: the implementing Delphi class on the first line and its `SolverID` on
  the second. **Blank** means the operation uses the shared default solver framework
  (and, when it has no separate solver, its container class computes the toolpath
  directly). Only operations with a dedicated solver show a value here.
- **Declared in** — the XML file (relative to the `Supplement` folder) that declares
  the descriptor. Open it to study the full descriptor.

> **Picking a base.** For a new milling operation the usual targets are
> `TST3DMillOp` (3D) or `TSTAbstract5DOp` (3D/5D), or a concrete sibling you want to
> resemble. For lathe, derive from `AbstractLatheOP` or `LatheContouringOp`. For an
> operation whose toolpath is computed by your own CAM API extension, derive from an
> extension base (e.g. `TSTMillExtensionOp`) and set `SolverID` to your extension's
> id - see [section 4.3](operation-xml-descriptors.md#3-the-operation-header).
